# 个人版本部署说明

代码仓库：`Halflinee/reelax-server`。
运行镜像：`ghcr.io/halflinee/reelax-server:latest`。

修改代码后提交到自己的 GitHub，由 Actions 检查并构建镜像，再让腾讯云服务器更新。
不需要在 2GB 内存的服务器上编译。上传的是程序代码，服务器的 `.env`、账号数据库和凭证不上传。
项目 `.npmrc` 将上游锁文件中的镜像源映射到官方 npm 源，以兼容 npm 12 的下载来源检查，不修改依赖版本或放宽安装策略。

## 1. 首次准备 GitHub

1. 在 GitHub 上 Fork `Creator2K/reelax-server`，Owner 选择 `Halflinee`，名称保留 `reelax-server`。
2. 打开自己的仓库，进入 **Actions**。若显示 Fork 工作流尚未启用，按页面提示启用。
3. 将本地准备好的更改提交到自己仓库的 `main`。之后每次提交都会运行 `CI`。
4. 等待 **类型检查 / Lint / 测试 / 构建** 和 **构建并推送镜像（GHCR）** 两项成功。
5. 首次镜像发布后，进入个人 GitHub 页面的 **Packages → reelax-server → Package settings**，将镜像可见性设为 **Public**。
   新镜像默认可能是 Private；Public 才能让服务器无需保存 GitHub 访问令牌就拉取。公开范围是程序镜像，镜像中不能包含个人凭证或私有数据。

需要手动构建时，在 **Actions → CI → Run workflow** 中选择 `main` 并运行。
工作流只在检查通过后发布镜像，PR 不发布。

## 3. 现有腾讯云服务器首次切换

以下步骤在 **OrcaTerm** 执行。每一步成功后再继续，任何一步报错都先停下检查。
只有备份时和重建应用容器时会短暂中断挂机。Caddy、免费网址和防火墙规则不需要重装。

### 保存当前设置和旧镜像信息

```bash
sudo -i
cd /opt/reelax-server
umask 077
backup_dir="/root/reelax-backups/$(date +%Y%m%d-%H%M%S)"
mkdir -p "$backup_dir"
cp -p .env docker-compose.yml "$backup_dir/"
docker inspect --format '{{.Image}}' reelax-server > "$backup_dir/image-id.txt"
```

首次切换前，确认项目目录中没有已有的 `docker-compose.override.yml`。如果存在，先比较内容，不直接覆盖。

### 下载个人配置并验证，先不停止旧程序

```bash
curl -fL https://raw.githubusercontent.com/Halflinee/reelax-server/main/docker-compose.override.yml -o "$backup_dir/docker-compose.override.yml.new"
docker compose -f docker-compose.yml -f "$backup_dir/docker-compose.override.yml.new" config -q
docker compose -f docker-compose.yml -f "$backup_dir/docker-compose.override.yml.new" config --images
docker compose -f docker-compose.yml -f "$backup_dir/docker-compose.override.yml.new" pull app
```

镜像列表应显示 `ghcr.io/halflinee/reelax-server:latest`。
如果拉取出现 `denied` 或 `unauthorized`，检查 GitHub Actions 是否已经成功发布，以及 Package 是否为 Public；不要继续停止旧程序。

### 暂停并备份完整数据，再切换镜像

保持同一个 OrcaTerm 窗口，依次执行：

```bash
docker compose stop app
docker cp reelax-server:/app/data "$backup_dir/data"
```

复制成功后继续；如果复制失败，执行 `docker compose start app` 恢复原程序，先处理备份错误。

```bash
cp "$backup_dir/docker-compose.override.yml.new" docker-compose.override.yml
docker compose up -d --no-build app
docker compose ps
curl -f http://127.0.0.1:8580/api/health
```

首次启动可能需要稍等，健康检查成功后刷新网站，确认原账号、配置和挂机状态。
`latest` 会指向个人仓库最近成功发布的版本；不能只靠应用版本号判断某次自定义改动是否已部署，可以结合 GitHub Actions 提交号和后台版本信息确认。

如果新版启动失败，查看 `docker compose logs --tail=80 app`，保留备份和旧镜像信息。新版可能迁移数据库，不应在未确认数据兼容时直接换回旧镜像。

备份中包含 `.env` 和账号资料，另存到自己的电脑时妥善保管，不公开上传。
不要删除数据卷、不要运行 `docker compose down -v`、不要重新生成 `MASTER_KEY`。
主配置中的项目名 `reelax-server` 和数据卷 `reelax-data` 必须保留。

## 4. 以后更新个人版本

1. 在电脑上修改、检查、提交并推送代码。
2. 等自己的 GitHub Actions 检查和镜像发布成功。
3. 在 OrcaTerm 执行一次 `sudo reelax-update`，自动下载、备份、更新并检查。

### 一次性安装更新命令

已经切换到个人镜像的服务器，在 OrcaTerm 执行以下整段。安装本身不会重启程序。

```bash
(
set -eu
script_file=$(mktemp)
trap 'rm -f "$script_file"' EXIT
curl -fL https://raw.githubusercontent.com/Halflinee/reelax-server/main/scripts/update-image.sh -o "$script_file"
bash -n "$script_file"
sudo install -o root -g root -m 755 "$script_file" /usr/local/sbin/reelax-update
echo "安装完成，以后执行 sudo reelax-update"
)
```

以后每次更新只运行：

```bash
sudo reelax-update
```

脚本先下载 `ghcr.io/halflinee/reelax-server:latest`，下载失败不会停止原程序。下载完成后保存 `.env`、两份 Compose 配置和旧镜像 ID，暂停 `app`，复制完整 `/app/data`（数据库、账号配置、日志、微信凭证等），随后启动新版并检查健康接口。Caddy 不重启。

备份保存在 `/root/reelax-backups/日期时间-随机后缀/`，目录中的 `backup.complete` 表示备份已完整复制。配置备份失败不会停机；停机后数据备份失败，会尝试重新启动原容器。新版启动或健康检查失败时明确报错，保留完整备份，不自动降级数据库。

备份只保存在服务器本机，含账号凭证和主密钥，仅 root 可读取。每次更新且健康检查成功后，自动保留最近 **5 次完整备份**，删除更早的完整备份（按目录名中的创建时间排序，同一秒内的旧备份按名称排序，当前备份始终保留）。更新失败时不清理；未完成的备份、手工创建的目录和符号链接不自动删除。重要备份另外下载保存。

脚本本身有修改时，重新执行一次安装步骤即可更新该命令；只更新 Docker 镜像不会更新宿主机上的 `reelax-update`。重新安装不会立刻清理备份，下一次执行 `sudo reelax-update` 且健康检查成功后才清理。

脚本通过个人覆盖配置选择镜像，不拉源码、不在服务器编译、不修改 `.env` 或数据卷。显式执行 `docker compose -f docker-compose.yml ...` 会忽略个人覆盖文件，日常更新请使用 `sudo reelax-update`。

作者后续有更新时，可通过 Fork 的 **Sync fork** 或在本地合并 `upstream/main` 引入；存在冲突时先处理和验证，不强制覆盖自己的功能。

## 5. 金币交易预览（个人版本 1.24.3）

更新后以普通用户进入控制台，侧边栏选择「金币交易预览」，选择自己已绑定的付款与收款账号，输入希望收款账号实际到账的金币数量，再点「生成预览」。页面读取双方当前金币、收款账号的市场配置和完整装备背包，展示预计支付、手续费、到账金额与一件回收价较低的候选装备。

此版本只提供 `GET /api/trade-preview`，没有上架、购买或确认交易接口；不会锁定、预留或转移装备，也不会启停挂机。预览中的数据并非成交保证，背包或余额变化后需要重新读取。已有自动卖装备功能仍按原配置运行，候选装备可能在后续被其处理。

不能选择同一账号或同一个游戏角色的重复记录，也不能读取其他用户的账号。未穿戴、未锁定、未上架且无需验证码的装备才能成为候选；魔法石不参与。真实税率、市场最低售价及挂单额度都从游戏读取，数据缺失时明确报错，不使用假定税率。

## 6. 专精鱼调配预览（个人版本 1.24.4）

普通用户进入「专精鱼调配预览」，选择出鱼和收鱼账号，点击「生成供需预览」。不需要手填鱼名或统一专精目标：分别从两个账号读取当前已解锁、非等待的专精目标和背包，按鱼种 ID 匹配缺口。可以点「对调方向」检查反方向的供需。

出鱼账号先留足自身当前专精所需，锁定、专精保护和带泰坦倍率的鱼不参与调配建议。自身保留与锁定保护可能重叠，不重复扣除。收鱼账号也先保留自身所需，再从其富余的同稀有度鱼中选取回交换鱼；优先补出鱼账号的专精缺口，同一批回交换库存仅分配一次。只展示直接一比一交换建议，不假定可以单向赠送、不自动搜索或执行多轮交换。

以物易物仅支持神话、奇异、奥秘鱼。其他稀有度仍展示供需，但不生成匿名市场定向转移方案。供给或回交换鱼不足、市场权限不可用时明确说明；资料读取失败不会伪装成「没有缺口」。有交换建议的鱼优先展示。

此版本只有 `GET /api/mastery-transfer-preview`，没有执行入口，不挂单、不解锁、不购买、不交换、不献祭，也不改动挂机模块。建议基于读取时的数据，未预留库存，也未验证实际挂单额度及最终成交；自动卖鱼、自动献祭或目标变化后需要重新读取。真实账号及页面效果需要更新后验证。

## 7. 金币集中手动交易（个人版本 1.24.5）

侧边栏「金币集中」保留原来的 `/trade-preview` 地址。选择付款和收款账号，输入希望实际到账的金币数量，先生成预览。预览不会发起游戏交易；条件满足时会显示「确认这笔交易」。弹窗列出双方账号、装备、预计支付、手续费和到账金额，点击「确认并交易」后才实际上架并购买。装备从收款账号转给付款账号。

一次确认绑定一份有效期 5 分钟的服务端预览。执行前重新核对账号归属、游戏角色、税率、余额和已选装备；条件变化就停止，不自动换装备或增加支付金额。实际请求只能购买本次已核对的指定订单。每条记录保存独立的挂单和购买幂等键，重复确认仅返回已有状态；关联游戏角色有进行中或待核对记录时不能再次发起交易。

新增 `0011_gold_transfers` 迁移仅添加交易记录表，原有账号与配置保留。最近记录会展示全部进行中、待核对记录以及最近 10 条已结束记录。只有双方新成交记录指向同一件装备、同一笔成交且金额与预览一致，才显示「已完成」；不根据余额变化猜测到账，避免挂机收益干扰核对。

如果挂单后失败、网络超时或服务重启，记录会保留为「需要核对」，不自动重试写操作，也不自动补转。先点「核对成交结果」（只读游戏成交记录）；仍无法确认时，到游戏内检查双方成交记录并取消仍未成交的挂单，再点击「已在游戏内核对，结束记录」。结束记录只解除后续操作限制，不退款、不撤单、不再次交易。订单公开上架期间可能被第三方购买，这种情况不能报告为本次指定双方交易完成。

本功能不提供批量归集、自动定时归集、验证码处理或异常订单自动撤销。实际游戏市场返回的挂单与成交数据若不符合可核对格式，会停止并明确报错。开发测试使用隔离数据库与模拟游戏接口，没有动用真实账号、真实金币；真实交易和界面效果需要用户在更新后手动验证，首次宜使用一笔可接受的小额交易。

## 8. 市场补齐专精鱼预览（个人版本 1.24.6）

进入「专精鱼调配预览」，选择两个账号并生成供需预览。在缺鱼的卡片中点击「查看限价购买预览」，按收鱼账号最新的专精缺口读取该鱼市场价格。不能以物易物的低稀有度鱼也能使用；市场购买无需出鱼账号提供库存或回交换鱼。

初次按市场允许的最低单价、当前金币余额和专精缺口预览，不自动抬价追逐卖盘。可调整「想买数量」「最高单价」「总预算」，再点「重新预览」。数量同时受最新缺口、市场单笔上限以及按最高单价冻结的金币限制；预计成交按当前读取的最多 50 档卖盘从低价累计，未立即成交的数量单独展示为等待部分。

此功能只有 `GET /api/mastery-transfer-preview/market`，没有实际下单入口，不挂单、不购买、不冻结金币、不献祭。鱼类市场匿名撮合，不能指定购买某个账号的鱼，也不能保证金币转给所选出鱼账号。预览不预留库存，市场、金币和专精目标变化后需要重新读取。实际账号返回数据及页面视觉效果仍需更新后验证。

## 9. 按需求选择供给并确认市场交易（个人版本 1.24.7）

侧边栏进入「专精鱼调配」，依次选择需求账号、地图区域、专精鱼，再点「生成供需预览」。地图和鱼种从需求账号当前已解锁、正在进行的专精目标读取，缺口扣除现有库存。默认列出本用户除需求账号以外的全部账号，分别显示所选鱼的库存、自身专精保留、锁定或倍率保护和可供数量；读取失败单独标出，不把错误当成零库存。不同服务器和实际登录同一需求角色的记录不能用作供给方。

选择一个供给账号，设置单价和数量，点击「生成交易预览」。预览检查最低单价、双方挂单额度、单笔数量上限、需求方余额、最新专精缺口、供给方余量及当前盘口。存在同价或更高买单、同价或更低卖单时不允许确认。点击「确认交易」后，弹窗会列出双方账号、鱼种、数量、价格、金币结算以及公开撮合风险；必须点击「接受公开撮合并交易」才真实挂单。

执行时先重新核对全部条件，需求方先挂买单，再确认该订单仍有效且完整未成交，复查保护库存、缺口、手续费和盘口，最后由供给方挂卖单。价格和数量不是订单身份，检查也不能锁住市场；检查后仍可能出现其他订单并被第三方撮合。只有双方新成交编号、鱼种、数量、单价、实际结算及本次两个订单完整对应，才显示完成。不会仅凭余额或库存变化推断成功，不自动补买或补卖。

预览有效期 5 分钟，重复点击只执行一次。同一游戏角色在金币集中或专精鱼交易中有进行中、待核对记录时，不能发起另一笔交易。新增迁移 `0012_fish_market_transfers` 仅创建交易记录表，保留原有账号和配置。超时、部分成交、数据无法核对或重启中断后进入「需要核对」，不自动恢复写操作；可点「核对成交结果」只读查询，仍无法确认时先到游戏内检查双方记录并取消剩余挂单，再手动结束记录。结束记录不撤单、不退款、不再次交易。挂单响应丢失且缺少订单编号时需人工核对，不凭价格数量猜测订单。

原有双账号以物易物预览和限价购买预览 API 保留，页面主流程改为金币市场调配，不修改原有挂机模块，也不自动解锁或献祭。开发验证使用隔离数据库和模拟游戏接口；真实账号接口数据、实际成交和页面视觉效果未验证。

2026-11-16 核对的[官方客户端](https://static.reelax.cn/assets/index-CfL6LcQZ.js)鱼类委托仅向 `POST /api/market/orders` 提交 `assetType: fish`、`side`、`fishId`、`quantity`、`limitUnitPrice`，未提供按鱼类买单 ID 成交的调用；盘口为匿名价格档。按订单 ID 的 `/purchase` 调用出现在装备购买流程。本功能因此使用公开盘口撮合，不将「价格加数量」当成指定订单。

## 10. 专精鱼读取提速（个人版本 1.24.8）

需求账号、市场配置和供给账号的独立数据并行读取。交易预览仅读取所选两个账号，每份账号快照及市场配置只读一次；不再先生成供需预览后重新读取相同数据。供给读取仍限制为最多三个账号并行，但空闲位置可以继续读取后续账号，不被某个慢账号拖住整批。

同一账号无取消信号的并发请求，在首次准备会话和临近到期续期时共享一次准备；带取消信号的请求保留独立取消语义。这不缓存金币、库存、专精目标或盘口，实际交易前的实时复查仍保留。

四账号模拟网络测试中，每个游戏请求固定耗时 100ms：供需等待从 300ms 降至 100ms，交易预览从 400ms 降至 100ms。这个结果用于验证程序减少了等待轮次，不代表真实服务器延迟；游戏接口、代理或网络本身较慢时，仍需等待实际响应。

## 11. 公共资料复用及超时定位（个人版本 1.24.9）

公共鱼种和地图资料成功读取并验证格式后，按游戏服务器在内存中复用十分钟。界面选地图、生成供需和查看报价共用这份资料；并发加载只下载一次，失败不缓存成成功，服务重启或十分钟到期后重新下载。只保存公开鱼种和地图字段，不跨账号复用余额、库存、专精目标、权限或盘口。

正式确认交易时使用独立的新公共资料请求，不借用预览缓存或正在进行的下载；原有余额、库存、身份、市场配置与盘口实时复查保留。首次读取、缓存到期和正式确认仍可能受服务器到游戏站点的慢链路影响，本修复不承诺网络恢复或绝不超时，也不延长原来的超时限制。

读取失败现在显示账号及接口类别，例如「需求账号：读取公共鱼种和地图资料失败，请求超时（30000ms）」，也会区分账号资料、专精目标、鱼获背包、市场配置和鱼类盘口。错误不返回请求头、凭证或原始响应体。若仍慢，优先根据具体接口和服务器上的实际网络测量继续定位，不把模拟测试耗时当成生产环境耗时。

## 12. 固定资料本地保存（个人版本 1.24.10）

固定地图和鱼种定义改为保存在现有 SQLite 数据库的 `game_catalogs` 表中，按游戏服务器分别保存，不再十分钟自动过期。首次没有本地资料时下载并验证后保存；后续选地图、生成供需、预览金额、正式确认交易都使用本地固定资料，不重新下载整份公共目录。程序更新和重启后仍能读取，现有 `/app/data` 数据卷备份也会包含它。

账号当前专精目标、解锁与等待状态、缺口、背包、锁定保护、余额、市场最低价配置、手续费、挂单额度和盘口仍实时读取。固定目录中的鱼名、地图名、稀有度和基础回收价使用本地值；游戏修改这些资料后，在「专精鱼调配」选择需求账号，再点「更新固定资料」手动下载新版。游戏接口仍会校验实际下单条件，不因本地资料复用而跳过账号或市场复查。

新增迁移 `0013_game_catalogs` 只创建公开资料表，原有账号、配置和交易记录保留。只有完整有效的公开鱼种和地图字段会保存，不写入凭证或额外私有字段。下载失败或资料不完整时不覆盖原有内容；本地内容损坏时明确提示更新，更新入口可以重新获取并恢复。出现目录未收录的新专精鱼或地图时，也会提示点击「更新固定资料」，不会猜测鱼种。

手动更新只获取公共资料，不挂单、不买卖、不解锁、不献祭。首次下载或主动更新仍可能受到服务器到游戏站点的慢链路影响；本次调整减少重复下载，不承诺网络质量改善。关闭并重新打开磁盘数据库、重建服务、手动更新失败保留旧内容及交易确认继续复查动态数据已纳入测试；真实服务器更新后的速度及界面效果仍需现场确认。

## 13. 自动选价并预览（个人版本 1.24.11）

生成专精鱼供需预览后，选择供给账号和数量，点击「自动选价并预览」，无需先手填价格。程序同一轮读取双方动态数据及最新盘口，选择满足市场底价、高于其他全部买单、低于其他全部卖单的最低整数价格。例如最高买价 100、最低卖价 120、底价不高于 101 时选择 101；没有买单时从底价开始，没有卖单时仍要高于最高买价。

若没有价格空档，或所选数量按最低可用价计算超过需求账号当前金币，明确显示盘口及原因，不自动减少数量、不选择会与已有订单立即撮合的价格。自动选价只生成预览及本地待确认记录，不挂单、不冻结金币。预览中显示当前最高买价、最低卖价、市场底价、选定价格、预计支付和供给方实收。仍可手填单价，使用「按填写价格预览」。

本功能使用只读 `GET /api/mastery-transfer-preview/auto-quote`，参数为两个账号、地图、鱼种和数量，不接受指定价格或执行参数。只有用户之后确认并接受公开撮合风险，才使用该份预览固定的价格执行交易。确认时不会再次自动选价，即使价格空档变化也不擅自增减金额；产生竞争订单、余额或库存等条件变化时停止，重新选价需用户主动操作。

固定资料继续使用本地保存的内容；自动预览不额外下载资料，也不先选价后再重复读取一轮账号和盘口。公开撮合仍无法锁定指定双方，检查后的新订单仍可能参与成交；原有双方实际订单、成交记录和金币结算核对保持。已覆盖选价边界、无空档、余额不足、越权、只读预览及确认固定价格的测试；真实成交和界面效果需更新后验证。

## 14. 鱼类市场行情扫描（个人版本 1.24.12）

侧栏「市场行情」选择一个有市场权限的账号、地图、鱼种（可选本地图全部）和每种鱼的试算数量，点击「开始扫描」。地图、鱼种沿用服务器本地公开资料。前端每批最多三种鱼，逐批显示结果，可停止后续批次；当前批次仍会完成。每批重新读取账号余额和市场配置，每种鱼读取前 50 档匿名汇总买卖盘。不自动定时轮询，不读取专精需求、库存或其他账号，不创建市场订单、交易记录或冻结金币。

每种鱼分别显示两种结果：现价往返按卖盘由低到高计算买入成本，再按买盘由高到低计算卖出收入，深度不足不按买一卖一乘全部数量；挂单预测在最高买价加一与市场底价中取较高者作为买入价，最低卖价减一作为卖出价，要求两者严格位于当前价差内且卖价高于买价。缺少单边报价、交叉盘口或没有整数空档时不虚构方案。低于当前市场底价的买盘不计入可卖深度。

读取最新 `sellerFeeBasisPoints`，按每条鱼税费向上取整作保守估算：税后净利润 = 卖出总额 - 估算税费 - 买入本金。显示税后收入、回报率和按同一数量计算的保本单价。不会按不足的余额或数量上限自动缩量；余额、单笔数量和现有挂单额度不满足时不列为可用机会。筛选中的最低净利润仅筛选当前已读取结果，每种鱼的本金独立计算，不能相加当作同时可买总量。

挂单预测假设低买和高卖两次都成交，无法确定等待时间或确保盈利；匿名盘口可能包含本人的订单，且各批读取时间不同，不能当作保证可执行的套利。买入后行情变化可能导致卖不出或亏损，实际税费和利润需按最终分笔成交核对。单个盘口错误保留为失败行，收益为未知；账号或配置读取失败停止后续批次并保留已读取结果。自动买卖不在本次范围内。

使用 `GET /api/mastery-transfer-preview/market-scan/options?accountId=...` 读取固定选项，`POST /api/mastery-transfer-preview/market-scan` 只读扫描，每批 1—3 个不重复的 `fishIds` 和正整数 `quantity`；请求不能带执行参数。接口继承登录、审批、账号归属和禁止缓存规则。无新增依赖或数据库迁移。真实市场速度及界面操作效果仍需服务器更新后验证。

## 15. 买入与挂卖分两次确认（个人版本 1.24.13）

「市场行情」保留只读扫描，有预期利润且本金、额度允许的鱼种新增「生成买入预览（不下单）」。预览重新读取账号、税率及盘口，固定所选鱼种、数量、买入限价和卖出限价，显示最多冻结金币及保守预期利润，有效五分钟。点击「确认买入」并接受公开成交风险后才挂买单；确认前会复查角色、服务器、余额、税率、底价、挂单额度及盘口。账号自身仍缺该鱼用于专精时不挂买单，以免买入后被预留。不会擅自减少数量或重新选价。

买单可能等待或部分成交，页面保留已买数量和实际支出。点击「核对成交（不下单）」读取自己的确定订单编号；仅买单全部成交才进入「已买足，等待确认挂卖」。买足不会自动挂卖，刷新页面和服务重启也不会自动触发。用户再次点击「按预览价挂卖」确认后，才按先前固定的数量和卖出限价挂单，不自动追价或降价。委托限价是买入最高价和卖出最低价，实际撮合可能以更优价格成交。

挂卖前再次核对买单完整成交和实际成本，税率、底价、单笔数量和挂单额度仍满足要求；当前持有量和可售余量都必须比买入前至少增加本次数量，避免将既有库存当作新增可售鱼。锁定、专精预留、售鱼、献祭或其他库存变化可能让挂卖停止。自动售鱼、献祭和游戏内手动操作可能与交易并发，请避免同时处理这批鱼；本功能不会修改挂机配置，库存检查不能锁住游戏端的其他操作。

卖单未全部成交时保留进度，完整利润保持未知，不将预期利润显示成已盈利。两笔都按准确编号核对全部成交后，使用买单实际支出、卖单实际收入及实际累计手续费计算本笔净利润，分笔取整或更优成交价也按实际记录结算。公开市场仍不保证等待时间或盈利，买入后可能卖不出；剩余订单需用户到游戏内取消或处理。

新增 `0014_fish_market_deals` 只创建交易记录表及索引，保留原账号、配置和记录，并随原数据库备份保存。买卖方向有独立、持久的幂等键，发送前持久保存即将提交的方向；请求已尝试但没有确定编号时进入待核对，不能按价格数量猜订单或再次发送。已保存编号可用只读核对恢复状态；缺少编号需游戏内人工核对。服务重启只把执行中请求转为待核对，等待买卖和已买足的记录保留，不恢复自动执行。

同一实际角色在同一游戏服务器一次处理一笔未完成买卖，跨平台用户的重复账号记录也受限制；未完成或待核对记录与金币集中、专精鱼调配互相占用。只有明确确认已在游戏内处理订单及鱼获，才可「结束记录」释放占用；这不会替用户退款、撤单或再次交易。不同游戏服务器不互相占用。查询与操作继承登录、审批、归属校验，买卖确认及人工结束均记录审计。

接口位于 `/api/mastery-transfer-preview/market-deals`：`POST /preview` 生成只读预览，`GET /` 和 `GET /:id` 读取本地记录，`POST /:id/buy`、`POST /:id/sell` 分别确认两个方向，`POST /:id/check` 只读核对，`POST /:id/close` 明确人工处理后结束记录。确认接口不接受覆盖价格、数量或自动挂卖字段。页面仅在本地执行状态更新时轮询本地记录，真实市场订单只在用户核对或确认时读取。真实页面操作和账号成交尚需更新后验证，自动化测试不代表已进行真实买卖。
